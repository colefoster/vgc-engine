A doubles battle simulator built to be branched.

vgc-engine is a from-scratch Pokémon battle simulator in Rust, designed for the people writing search and learning code: MCTS rollouts, endgame solvers, self-play data. Fixed-size state, a heap-free step(), cheap clones and a Python module you can import.

Read the quickstart Download the spec sheet .md

Pokémon Showdown is the compatibility oracle. vgc-engine is not yet a drop-in replacement for it. See where it stands.

01 · Who it's for

For developers who need to play out a turn thousands of times.

Pokémon Showdown is the reference simulator, but it is JavaScript, event-driven and allocation-heavy. That is fine for a ladder. It is a bottleneck when a search tree wants to clone a battle, try every joint action and step each branch. vgc-engine is written for that loop.

Search & planning

Clone a battle, enumerate legal choices per slot, step each joint action, keep the best. Battle has no interior sharing, so a copy is a full independent state.

ML pipelines

A pyo3 module, vgc_engine, plugs into Python training and evaluation code. State round-trips through compact bytes or inspectable JSON.

Game-theory & endgames

The vgc-solver crate enumerates outcome frontiers and solves small endgames, returning mixed policies for both sides with provenance and node counts.

Mechanics & tooling

A vgc CLI for damage, speed and EV questions, team legality checks for the Champions regulations, and a differential harness against Showdown.

What it is not

  • Not a bot. It doesn't play, ladder or make decisions. It simulates the turns your code chooses.
  • Not a cartridge emulator. Bit-exact reproduction of in-game RNG quirks is a non-goal.
  • Not outside competitive battling. No overworld, breeding or contests.

02 · Inside the engine

Data-oriented from the battle struct up.

The design takes its discipline from pkmn/engine and its answers from Pokémon Showdown, then aims both at modern doubles.

  1. A

    Fixed-size state, heap-free step

    Battle state is a plain fixed-size struct. Handles, not pointers: MonId, MoveId, SideRef. The project rule is no heap allocation inside step(), and an allocation probe over 500 battles reports 0 step allocations at the final implementation.

  2. B

    Tables generated at build time

    build.rs turns @pkmn/dex JSON into Rust source for species, moves, items, abilities and the type chart. Champions is a data overlay, not a fork of the code.

  3. C

    Doubles as a first-class format

    Slot targeting, spread-move damage, redirection, the Protect family, weather, terrain, screens, Tailwind and Trick Room live in shared modules. Format is orthogonal to generation.

  4. D

    Two Gen 9 doubles rule sets

    Standard Gen 9 doubles with Terastallization, and the Champions overlay (Reg M-B, Reg M-C) with Mega Evolution, Stat Points and Champions move data, selected by format id.

  5. E

    Chance frontiers on demand

    Behind the chance feature, Battle::step_chance() returns every possible next state of one turn with its prior. Today it wraps a record-and-replay pass. Native per-site branching is planned.

  6. F

    Showdown's own PRNG, opt-in

    The ps-rng feature adds a bit-exact port of Showdown's PRNG with its draw order and a per-draw trace, for seeded differential testing. Off by default, and absent from default builds.

The four passes match the documented v1 algorithm in vgc-solver: record the visited draw sites, take the cross product of their outcomes, replay each cell with a keyed RNG, and merge by canonical state hash. The toy keeps three site kinds per hit (accuracy, crit, 16 damage rolls). Real turns have more.

04 · Quickstart

From a team list to a branched turn.

These snippets use the Python and CLI surfaces as they exist in the source today. The Python API is still wire-level: choices are plain tuples and will become proper objects later.

# Build the wheel from crates/vgc-engine-py with maturin, then:
import json, vgc_engine

team = json.dumps([
    {"species": "rillaboom", "moves": ["protect"]},
] * 2)

b = vgc_engine.Battle.from_teams(team, team,
        format="gen9doublescustomgame", seed=7)

# Choices are (kind, actor_slot, move_or_team_idx, target_side, target_slot)
p1 = [b.legal_choices(0, s)[0] for s in (0, 1)]
p2 = [b.legal_choices(1, s)[0] for s in (0, 1)]

branch = b.clone()                  # independent copy, no shared state
result = branch.step_move(p1, p2)   # "continue" | "p1_win" | "p2_win" | "tie"

snapshot = branch.to_bytes()        # compact; to_json() for inspection
again = vgc_engine.Battle.from_bytes(snapshot)
import vgc_engine

# Exact endgame search with an HP-ratio leaf; returns mixed policies.
sol = vgc_engine.solve_endgame_exact(b, max_depth=4, node_budget=100_000)
sol["value"], sol["provenance"], sol["nodes_visited"]
row_action = sol["row_joint_policy"][0][0]   # an executable joint choice

# Or plug in your own batched leaf evaluator (a model, a heuristic…)
sol = vgc_engine.solve_endgame(b, lambda obs: [0.0] * len(obs))

# Champions team legality from a Showdown export
problems = vgc_engine.parse_and_verify(paste_text, format="regmb")
assert problems == []

# Quick damage range
r = vgc_engine.calc("chomp", "lando", "eq")
r["min"], r["max"]
# Test the default workspace (the pyo3 crate builds separately)
cargo test --workspace --exclude vgc-engine-py

# The `vgc` fast-calc front end: terse specs and aliases
cargo run --release -p vgc-engine-cli --bin vgc -- calc chomp lando eq
cargo run --release -p vgc-engine-cli --bin vgc -- survives chomp lando eq
cargo run --release -p vgc-engine-cli --bin vgc -- outspeeds chomp lando

# Opt-in instrumentation lives behind Cargo features
cargo test -p vgc-engine-core --features chance
cargo test -p vgc-engine-core --features ps-rng

06 · Evidence ledger

What has been measured, and what hasn't passed yet.

The project labels every number by how current it is. This page keeps those labels. The headline: the engine is not finished and the finish line is not met. The original phase gates remain binding; any revised accuracy gate or sampling protocol is still an open decision.

Current Final implementation, 2026-10-06

  • 1,546default-workspace tests pass, 0 fail (32 ignored)
  • 1,586tests pass with the ps-rng feature, 0 fail
  • 0step allocations in an allocation probe (500 battles, none capped)
  • 72/72bounded Quick Claw and Custap control cases match Showdown, keyed and seeded
  • 27Python binding tests pass against a freshly built wheel

Diagnostic Not an accepted gate sample

  • ~2×gap between keyed and seeded comparison modes on synthetic Reg M-B studies: 84.9% vs 42.6% state-clean battles on a 1,000-case development set. The samples reuse teams, so they are not an independent holdout or an accepted gate sample.
  • 3open residual issues triaged: White Herb timing, Hunger Switch missing, one unresolved HP divergence.
  • —Speed claims are withheld. The one consumer benchmark is a single synthetic workload awaiting acceptance.

Historical 2026-09 accuracy study

With every random outcome forced to match Showdown, most remaining divergences on real-game Reg M-C battles were deterministic mechanics bugs, not RNG. The PRNG port itself was bit-exact. That finding set the current fix-one-mechanic-at-a-time workflow.

07 · Roadmap

Modern doubles first. Every other generation later.

The long-term goal is one shared codebase across all generations and formats. Today, only Gen 9 doubles is being built.

Implemented

  • Gen 9 doubles core: targeting, spread damage, redirection, Protect family, weather, terrain, screens, Tailwind, Trick Room
  • Terastallization
  • Champions overlay: Mega Evolution, Stat Points, Reg M-B / M-C rules
  • Python bindings: build, step, clone, snapshot, legal choices
  • chance frontier (record/replay wrapper)
  • ps-rng Showdown PRNG mode
  • Endgame solver, damage-calc CLI, golden & conformance harnesses

In progress

  • Climbing the mechanic long tail found by the differential harness
  • Fixing the triaged residual issues one at a time, then re-scoring the synthetic studies
  • Deciding whether to revise the accuracy gate or sampling protocol, and which consumer rollout path counts
  • Agreeing a representative workload for the performance gate

Future

  • Native per-site chance branching with copy-on-write state
  • Earlier generations, newest first (Gen 8 → 1), as negative deltas on shared code
  • A stable C ABI
  • Possibly a WASM build for browser tools

08 · Straight answers

Questions worth asking first.

Is it accurate enough to replace Showdown?

Not yet. Targeted comparisons and scripted golden battles are green, but synthetic studies still show state divergences, the keyed and seeded comparison modes disagree, and the finish line is not met. Any revised accuracy gate or sampling protocol is still an open decision. Treat Showdown as ground truth and vgc-engine as a fast approximation under active correction.

How much faster is it?

The design targets order-of-magnitude speedups for rollouts, and that is what the Phase 4 gate will measure. No speedup is claimed here until a representative workload is agreed and re-measured.

Which generations and formats work?

Gen 9 doubles: the standard Tera-legal rules and the Champions overlay. Earlier generations have not been started. Singles exists as a format value, but doubles is the target.

Can I make it match Showdown's random numbers?

Yes, for testing. Build with ps-rng and seed a battle with a Showdown seed string. Draw order is aligned at the call sites the engine can mirror, with a trace of every draw.
