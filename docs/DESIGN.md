# DESIGN

## Language: Rust

- Same speed class as Zig / C / C++.
- `pyo3` gives near-zero-overhead Python bindings (mimikyu's trainer + `/decide` server import `vgc-engine` as a native module).
- `rayon` gives parallel rollouts (one MCTS call → N battles fanned out across cores) without hand-rolling threads.
- Bigger ecosystem than Zig; lower mental tax than C++; no GC tail-latency surprises like Go/JVM.
- Borrow checker is acceptable cost; battle state is mostly fixed-size structs anyway.

Not Zig: small ecosystem, no Python story, and the only Zig advantage (matching pkmn/engine syntactically) doesn't pay off because we are not forking pkmn/engine.

## Architectural principles (lifted from pkmn/engine's DESIGN.md, validated)

1. **Data-oriented.** Battle state is a fixed-size POD struct. No `Box`, no `Vec`, no `HashMap` inside the hot loop. Lookups are perfect-hash or direct-indexed arrays generated at build time.
2. **Zero heap allocation per turn.** All scratch buffers live on the stack or in pre-sized arenas held by the caller.
3. **Comptime / build-time everything.** Move tables, type chart, ability dispatch tables, learnset bitmaps — all generated by `build.rs` from JSON dumps of `@pkmn/dex` (+ Champions mod overlay where relevant).
4. **Handles, not pointers.** `MonId(u8)`, `MoveId(u16)`, `SideRef(u8)`. Trivially `Copy`. Serialize as bytes.
5. **Feature-flagged instrumentation.** `--features log` emits PS-style protocol; `--features chance` emits MCTS-ready probability frontiers (à la pkmn/engine's `chance.zig`); `--features calc` lets you pin RNG outcomes for tests. Off by default; zero cost when off.
6. **Generations are *not* greenfield siblings.** This is where we diverge from pkmn/engine. We expect 80%+ mechanic reuse from gen 5 onward (abilities/items/weather/terrain are stable). Earlier gens are encoded as *negative deltas* (no abilities pre-gen-3, no held items pre-gen-2, etc.) selected at runtime via a `Generation` enum dispatched in a single match per turn. Code duplication only where mechanics genuinely diverge (gen-1 crit formula, gen-2 spike stacking, etc.).
7. **Format is orthogonal to generation.** Singles vs. doubles vs. triples is a const generic / enum on the `Battle` type, not a separate codepath per gen. Targeting, redirection, spread moves all live in one shared module.
8. **Mods are data, not code.** Champions VGC = `@pkmn/dex` JSON + a Champions overlay JSON; no Rust code per mod, only data registration.

## Bindings

- **Primary:** `pyo3` crate `vgc-engine-py` exposing `Battle`, `Choice`, `Result`, `step(battle, p1_choice, p2_choice) -> Result`. Built as a wheel for the mimikyu venv.
- **Secondary (later):** stable C ABI (`vgc-engine-c`, `vgc-engine.h`) for the ps_bot C++ codebase to link directly if we ever want to replace the `/decide` HTTP hop.
- **Tertiary (maybe):** WASM build for browser-side analysis tools.

## RNG

- Pluggable RNG trait. Default impl: PCG64. Cartridge-faithful gen-1 / gen-3 LCG impls available behind a feature flag for the long-tail of users who want bit-exactness.
- For MCTS: deterministic seed in, `Frontier<Outcome>` out (enumerated probability tree) — copied directly from pkmn/engine's chance-mode design.

## Testing

Three layers, in dependency order. Each tier MUST be green before the next:

1. **Unit:** every move, ability, item exercised in isolation against a known outcome. Generated from a corpus of "minimal repro" battle states.
2. **Replay differential:** load a PS replay, step `vgc-engine` turn-by-turn with the same choices, diff state. Target ≥95% turn-agreement on the mimikyu corpus before declaring a gen/format "shipped."
3. **Live differential (CI nightly):** spin up a sandboxed PS server, play N self-play battles through both sims, diff at the protocol level. Catches things the static replay corpus doesn't cover.

## Performance targets (gen 9 doubles, no logging)

- Single rollout: ≤10µs/turn on one core (vs. PS's ~1ms).
- Batched: ≥1M turns/sec/core for MCTS leaf evaluation.
- Cold-start: `Battle` construction ≤1µs.

These are aspirational, not gates. The phase 1 gate is "correct + faster than PS by ≥10×."

## What we explicitly borrow from pkmn/engine

- Data layout discipline (read `pkmn/engine`'s `src/lib/gen1/data.zig` before touching ours).
- Chance/calc instrumentation pattern (see `src/lib/gen1/chance.zig`).
- The `transitions` / `MAX_FRONTIER_SIZE` MCTS API shape.
- The protocol log format (so existing PS replay tooling works on our output).

## What we explicitly reject from pkmn/engine

- "Each gen is its own crate." We share aggressively across gens 5–9 and treat earlier gens as feature-removal.
- Z3-proven `MAX_LOGS` bounds. Useful but the ROI doesn't fit our scope; we'll use generous static buffers + debug assertions.
- Zig-compiler-treadmill maintenance. Rust's stability guarantees buy us back the time scheibo spends chasing nightly.
